# SaaS Code Review

## Overall CR

The two SaaS apps have a clear control-plane versus tenant-runtime split, which is the right architecture for Cloudflare Workers and Durable Objects. The main risks are not structural; they are tenant isolation, authorization, webhook trust, route-contract drift, and session hardening.

The highest-priority issue is in the shared OIDC provider: static in-memory caches can cross tenant boundaries when Durable Objects share an isolate. The next tier of risk is public webhook handling and role authorization, where forged billing events or low-privilege tenant members can mutate production state. Blog SaaS is also currently not type-safe enough to trust for deployment: the typecheck catches real Remix route and middleware contract bugs.

Before production hardening, I would prioritize these in order: remove cross-tenant static caches, fix webhook verification/product validation, add tenant role authorization, repair middleware composition, add CSRF/session hardening, fix Blog SaaS route params/session serialization, and add router-level tests around these flows.

## apps/auth-saas

- Critical: Viewer tenant members can mutate OAuth clients, resources, users, secrets, sessions, and other tenant state. References: `apps/auth-saas/app/models/tenant-member.ts:10`, `apps/auth-saas/app/http/middleware/tenant-owner.ts:36`, `apps/auth-saas/bootstrap/app.ts:60`, `apps/auth-saas/bootstrap/app.ts:82`, `apps/auth-saas/app/http/controllers/dashboard/tenants/clients.ts:406`, `apps/auth-saas/app/http/controllers/dashboard/tenants/resources.ts:280`, `apps/auth-saas/app/http/controllers/dashboard/tenants/users.ts:474`. Why it matters: the model describes `viewer` as read-only, but `tenantOwner` admits any member role and mutating controllers do not check `tenant.role`. Fix: add role middleware for mutating tenant routes and enforce owner/admin-only or owner-only policies per route.

- High: Branding, hostname, and billing mappings overwrite controller middleware. References: `apps/auth-saas/bootstrap/app.ts:77`, `apps/auth-saas/bootstrap/app.ts:78`, `apps/auth-saas/bootstrap/app.ts:79`, `apps/auth-saas/app/http/controllers/dashboard/tenants/branding.ts:20`, `apps/auth-saas/app/http/controllers/dashboard/tenants/hostname.ts:20`, `apps/auth-saas/app/http/controllers/dashboard/tenants/billing.ts:13`. Why it matters: route mappings replace the controller's own `tenantOwner` and `subscription` middleware, causing missing context, 500s, and bypassed checks. Fix: compose middleware, for example `middleware: [...dashboard, tenantOwner, subscription]`, or preserve each controller's middleware when mapping.

- High: Newly created default tenant hostnames are not routed by repo config. References: `apps/auth-saas/app/http/controllers/dashboard/tenants.ts:322`, `apps/auth-saas/app/http/controllers/dashboard/tenants.ts:335`, `apps/auth-saas/app/models/hostname.ts:42`, `apps/auth-saas/wrangler.jsonc:21`. Why it matters: tenant creation provisions `${slug}.${PLATFORM_DOMAIN}`, but the Worker routes only include the platform domain and two fixed `sso.*` hosts. Fix: add a wildcard route such as `*.auth.sergiodxa.com/*` or provision defaults under a routed hostname pattern.

- High: Hostname-to-tenant KV cache never expires and is not invalidated. References: `apps/auth-saas/bootstrap/worker.ts:67`, `apps/auth-saas/bootstrap/worker.ts:83`, `apps/auth-saas/app/models/hostname.ts:154`, `apps/auth-saas/app/models/hostname.ts:170`. Why it matters: deleted or reassigned hostnames can continue routing to the old tenant indefinitely. Fix: use a short TTL and invalidate KV on hostname delete, activation, refresh, tenant suspension, and tenant deletion.

- High: Polar webhook verification does not match Polar Standard Webhooks. References: `apps/auth-saas/app/http/controllers/api/webhooks/polar.ts:68`, `apps/auth-saas/app/http/controllers/api/webhooks/polar.ts:113`, `apps/auth-saas/node_modules/@polar-sh/sdk/src/webhooks.ts:135`. Why it matters: the app expects `X-Polar-Signature` and custom HMAC verification, while the installed SDK exposes `validateEvent(body, headers, secret)`. Real Polar deliveries are likely rejected when the secret is configured. Fix: use `validateEvent` and handle `WebhookVerificationError`.

- Medium: Custom hostname activation does not update tenant issuer. References: `apps/auth-saas/app/http/controllers/dashboard/tenants.ts:331`, `apps/auth-saas/app/http/controllers/dashboard/tenants/hostname.ts:202`, `apps/auth-saas/app/models/hostname.ts:133`, `packages/oidc-provider/src/discovery/controllers/oidc.ts:14`. Why it matters: discovery, tokens, and WebAuthn RP IDs can remain tied to the default hostname even after a custom domain becomes canonical. Fix: call `tenantApi.setup({ issuer, region })` when a custom hostname becomes active and reset on deletion if needed.

- Medium: Platform session lifecycle is not hardened. References: `apps/auth-saas/app/http/controllers/onboarding/callback.ts:159`, `apps/auth-saas/app/lib/platform-session.ts:135`, `apps/auth-saas/app/http/controllers/dashboard/index.ts:62`, `apps/auth-saas/resources/layouts/document.ts:86`, `apps/auth-saas/app/http/middleware/session.ts:49`. Why it matters: the session cookie is manually set without `Secure`, sign-out links do not clear it, and the 30-day HMAC token is trusted without server-side revocation. Fix: use `createSessionCookie`, add a POST logout route that clears/revokes the session, and consider validating `sid` against tenant session state.

## apps/blog-saas

- Critical: Polar webhook authentication is a stub. References: `apps/blog-saas/app/services/polar.ts:68`, `apps/blog-saas/app/services/polar.ts:72`, `apps/blog-saas/app/http/controllers/api/webhooks/polar.ts:27`, `apps/blog-saas/app/http/controllers/api/webhooks/polar.ts:40`. Why it matters: any public caller can spoof billing metadata, attach a customer id, activate subscriptions, or suspend/reactivate another account's blogs. Fix: verify with Polar's webhook validator and `POLAR_WEBHOOK_SECRET`, then validate event idempotency, product id, customer id, and account ownership.

- High: Cookie-authenticated mutations have no CSRF protection. References: `apps/blog-saas/bootstrap/app.ts:27`, `apps/blog-saas/app/http/middleware/session.ts:33`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:43`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:132`, `apps/blog-saas/app/http/controllers/dashboard/billing.tsx:39`, `packages/blog-engine/src/engine.ts:51`. Why it matters: SameSite=Lax is not enough when tenant subdomains may be same-site with the platform and can host user-controlled pages. Fix: add synchronizer-token CSRF or strict Origin/Fetch-Metadata validation that does not trust same-site tenant origins.

- High: Blog resource handlers use the wrong route param. References: `apps/blog-saas/routes/web.ts:27`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:84`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:85`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:143`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:167`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:186`. Why it matters: `resources("/dashboard/blogs", ...)` generates `:id`, but handlers read `ctx.params.blogId`, so show/edit/update/delete fail. Fix: use `ctx.params.id` or configure the resource param name.

- High: Dashboard sessions cannot persist OIDC state correctly. References: `apps/blog-saas/app/http/middleware/session.ts:43`, `apps/blog-saas/app/http/middleware/session.ts:51`, `apps/blog-saas/app/http/controllers/auth.tsx:35`, `apps/blog-saas/app/http/controllers/auth.tsx:55`. Why it matters: `createCookie` serializes strings, but the middleware casts the parsed cookie to `SessionData` and serializes an object, so PKCE/state cannot reliably round-trip. Fix: use `remix/session` storage or explicitly JSON stringify/parse with schema validation.

- High: Activating a custom domain can lock owners out of tenant CMS auth. References: `apps/blog-saas/app/services/blog-provisioner.ts:155`, `apps/blog-saas/app/services/blog-provisioner.ts:167`, `apps/blog-saas/bootstrap/tenant.ts:136`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:93`, `packages/blog-engine/src/auth/controllers/auth.tsx:37`. Why it matters: the per-blog OIDC client is provisioned with only the subdomain callback, but custom-domain activation disables the subdomain and the engine derives callback URI from the current host. Fix: update the OIDC client redirect URIs before activation or keep the subdomain CMS/auth path available.

- High: Blog SaaS currently fails typecheck. References: `apps/blog-saas/app/http/middleware/session.ts:51`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:85`, `apps/blog-saas/bootstrap/worker.ts:116`. Why it matters: the failures include real Remix route and middleware contract bugs, not just cosmetic type issues. Fix: preserve middleware context types, align routes and handlers, remove the extra `createDashboardRouter(logger)` argument, and address package-level type errors that block the app.

- Medium: Billing entitlement is not enforced when creating active blogs. References: `apps/blog-saas/app/http/controllers/dashboard/index.tsx:38`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:68`, `apps/blog-saas/app/models/subscription.ts:44`, `apps/blog-saas/app/services/blog-provisioner.ts:62`. Why it matters: any signed-in account can provision an active blog without an active or trialing subscription. Fix: check `Subscription.isActive()` before showing/processing creation, or provision as suspended until entitlement is active.

- Medium: Polar webhook status/product validation can grant wrong entitlements. References: `apps/blog-saas/app/http/controllers/api/webhooks/polar.ts:47`, `apps/blog-saas/app/http/controllers/api/webhooks/polar.ts:71`, `apps/blog-saas/app/http/controllers/api/webhooks/polar.ts:80`, `apps/blog-saas/app/services/polar.ts:27`. Why it matters: unknown statuses default to `active`, and `product_id` is stored but not checked against `POLAR_PRODUCT_ID`. Fix: require the expected product id and fail closed on unknown statuses.

- Medium: Platform OIDC ID token validation accepts missing required claims. References: `apps/blog-saas/app/lib/oidc.ts:106`, `apps/blog-saas/app/lib/oidc.ts:122`, `apps/blog-saas/app/lib/oidc.ts:125`, `apps/blog-saas/app/lib/oidc.ts:128`, `apps/blog-saas/app/http/controllers/auth.tsx:72`. Why it matters: a malformed ID token without issuer, audience, or expiration can still create an account if it has `sub`. Fix: require `iss`, `aud`, and `exp`, and consider nonce/iat validation.

- Medium: Custom-hostname creation can leak orphan Cloudflare resources. References: `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:249`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:255`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:257`, `apps/blog-saas/database/migrations/0001-init.sql:30`, `apps/blog-saas/app/services/hostname.ts:37`. Why it matters: the controller creates the Cloudflare custom hostname before inserting the D1 row; if persistence fails, Cloudflare keeps an orphan hostname. Fix: pre-check local constraints and delete the just-created Cloudflare hostname if local persistence fails.

- Low: Blog region is type-cast instead of validated. References: `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:20`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:72`, `apps/blog-saas/app/http/controllers/dashboard/blogs.tsx:73`, `apps/blog-saas/app/services/blog-provisioner.ts:133`, `apps/blog-saas/bootstrap/worker.ts:36`. Why it matters: forged form data can persist an arbitrary region string that is later cast to `DurableObjectLocationHint`. Fix: validate `region` against `REGIONS` before provisioning.

## packages/oidc-provider

- Critical: Tenant metadata and signing-key caches are static and can leak across tenants. References: `packages/oidc-provider/src/management/models/tenant-meta.ts:23`, `packages/oidc-provider/src/management/models/tenant-meta.ts:87`, `packages/oidc-provider/src/signing-keys/models/signing-key.ts:27`, `packages/oidc-provider/src/signing-keys/models/signing-key.ts:87`, `apps/auth-saas/bootstrap/tenant.ts:16`, `packages/oidc-provider/src/oauth/controllers/token.ts:204`. Why it matters: multiple Durable Object tenant instances can share one Worker isolate, so one tenant can reuse another tenant's issuer or signing keys. Fix: remove static caches or key them by tenant/provider/database instance.

- High: Client credentials can mint access tokens for arbitrary audiences/resources. References: `packages/oidc-provider/src/clients/models/client.ts:59`, `packages/oidc-provider/src/clients/models/client.ts:125`, `packages/oidc-provider/src/oauth/controllers/token.ts:503`, `packages/oidc-provider/src/oauth/controllers/token.ts:507`. Why it matters: `allowed_resources` exists but is not enforced against the requested `resource` parameter. Fix: validate each requested resource against registered resources and the client's allowed resources.

- Medium: Refresh tokens are issued even when `offline_access` was not requested. References: `packages/oidc-provider/src/discovery/controllers/oidc.ts:36`, `packages/oidc-provider/src/oauth/controllers/token.ts:281`, `packages/oidc-provider/src/oauth/controllers/token.ts:286`. Why it matters: all authorization-code clients receive long-lived refresh capability by default. Fix: only issue refresh tokens when `offline_access` is requested and allowed, and consider token rotation.

## packages/blog-engine

- Medium: Tenant login has an open redirect through `next`. References: `packages/blog-engine/src/auth/controllers/auth.tsx:33`, `packages/blog-engine/src/auth/controllers/auth.tsx:63`, `packages/blog-engine/src/auth/controllers/auth.tsx:86`. Why it matters: `safeNext()` accepts any value starting with `/`, including protocol-relative URLs such as `//evil.example`. Fix: reject `//...`, normalize with `new URL(value, request.url)`, and require the resolved origin to match the request origin.

- Medium: SQL sessions ignore server-side expiry on read. References: `packages/blog-engine/src/database/session-storage.ts:30`, `packages/blog-engine/src/database/session-storage.ts:34`, `packages/blog-engine/src/database/session-storage.ts:52`. Why it matters: `expires_at` is written but not checked, so a presented session id can be accepted after stored expiry if the cookie is still sent. Fix: compare `expires_at` to `Date.now()`, delete expired rows, and return a fresh empty session.

- `bun run --cwd apps/blog-saas typecheck` fails with Remix route contract, middleware context, session serialization, and shared blog-engine type errors.

- `apps/auth-saas` only has `apps/auth-saas/app/lib/crypto-utils.test.ts`.
