PKCE (Proof Key for Code Exchange, pronounced "pixie") is a security extension for OAuth 2.0 that prevents authorization code interception attacks. Originally designed for mobile and native applications, PKCE is now required for public clients in OAuth 2.1 and recommended for all OAuth flows.

The PKCE flow adds two parameters to the OAuth authorization process: a **code verifier** (a cryptographically random string generated by the client) and a **code challenge** (a transformation of the verifier sent to the authorization server). When the client exchanges the authorization code for tokens, it sends the original code verifier. The authorization server transforms the verifier and compares it to the stored challenge. If they match, the server knows this is the same client that initiated the authorization request.

This tutorial walks through implementing both the client side generation and server side verification of PKCE code challenges.

## Generate the Code Verifier

The code verifier must be a high entropy cryptographic random string between 43 and 128 characters.

```ts {% path="lib/pkce.ts" %}
function generateCodeVerifier(): string {
	let bytes = new Uint8Array(32);
	crypto.getRandomValues(bytes);
	return base64UrlEncode(bytes);
}

function base64UrlEncode(bytes: Uint8Array): string {
	let binary = String.fromCharCode(...bytes);
	return btoa(binary).replace(/\+/g, "-").replace(/\//g, "_").replace(/=/g, "");
}
```

The `base64UrlEncode` function converts raw bytes to a URL safe base64 string by replacing `+` with `-`, `/` with `_`, and removing padding `=` characters. This produces a 43 character string from 32 random bytes, meeting the minimum length requirement.

## Store the Verifier Securely

Store this verifier securely on the client side. For browser applications, use an HTTP only cookie. For native applications, use secure storage.

```ts {% path="lib/pkce.ts" %}
let codeVerifier = generateCodeVerifier();
let cookieValue = base64UrlEncode(
	new TextEncoder().encode(
		JSON.stringify({
			codeVerifier,
			state: crypto.randomUUID(),
		}),
	),
);

// Set as HTTP-only cookie with short expiration
let cookie = `__oauth_state=${cookieValue}; Path=/; HttpOnly; SameSite=Lax; Max-Age=600`;
```

The cookie expires in 10 minutes, matching the typical authorization code lifetime. Including the CSRF state token in the same cookie simplifies storage while maintaining security.

## Generate the Code Challenge

The code challenge is derived from the code verifier. RFC 7636 defines two methods: **plain** (the challenge is identical to the verifier, not recommended) and **S256** (the challenge is the SHA-256 hash of the verifier, base64url encoded, recommended).

Always use S256 when supported. It prevents the challenge from revealing information about the verifier.

```ts {% path="lib/pkce.ts" %}
async function generateCodeChallenge(verifier: string): Promise<string> {
	let encoder = new TextEncoder();
	let data = encoder.encode(verifier);
	let hash = await crypto.subtle.digest("SHA-256", data);
	return base64UrlEncode(new Uint8Array(hash));
}
```

This function encodes the verifier as UTF-8 bytes, computes the SHA-256 hash, and converts the result to a base64url string. The output is always 43 characters, representing the 256 bit hash.

## Include the Challenge in the Authorization Request

Send the code challenge and method with your authorization request.

```ts {% path="lib/authorize.ts" %}
let codeVerifier = generateCodeVerifier();
let codeChallenge = await generateCodeChallenge(codeVerifier);

let authorizeUrl = new URL("/authorize", "https://auth.example.com");
authorizeUrl.searchParams.set("response_type", "code");
authorizeUrl.searchParams.set("client_id", "your-client-id");
authorizeUrl.searchParams.set("redirect_uri", "https://app.example.com/callback");
authorizeUrl.searchParams.set("scope", "openid email profile");
authorizeUrl.searchParams.set("state", crypto.randomUUID());
authorizeUrl.searchParams.set("code_challenge", codeChallenge);
authorizeUrl.searchParams.set("code_challenge_method", "S256");
```

The authorization server stores the challenge and method alongside the authorization code. When advertising PKCE support in your OAuth discovery documents, include the supported methods.

```ts {% path="lib/discovery.ts" %}
{
	code_challenge_methods_supported: ["S256", "plain"];
}
```

## Store the Challenge with the Authorization Code

On the server side, store PKCE parameters when creating authorization codes.

```ts {% path="db/schema.ts" %}
import * as s from "remix/data-schema";
import { createTable } from "remix/data-table";

let authorizationCodeTable = createTable({
	name: "authorization_codes",
	primaryKey: ["code"],
	columns: {
		code: s.string(),
		client_id: s.string(),
		subject_id: s.string(),
		session_id: s.string(),
		redirect_uri: s.string(),
		scope: s.nullable(s.string()),
		nonce: s.nullable(s.string()),
		pkce_challenge: s.nullable(s.string()),
		pkce_method: s.nullable(s.enum_(["S256", "plain"])),
		auth_time: s.number(),
		expires_at: s.number(),
		created_at: s.number(),
	},
});
```

When creating the authorization code, capture the PKCE parameters from the authorization request.

```ts {% path="lib/authorization-code.ts" %}
async function createAuthorizationCode(
	db: Database,
	data: {
		clientId: string;
		subjectId: string;
		sessionId: string;
		redirectUri: string;
		scope?: string[];
		nonce?: string;
		pkce?: { challenge: string; method: "S256" | "plain" };
	},
) {
	let code = crypto.randomUUID();
	let now = Date.now();
	let TTL = 10 * 60 * 1000; // 10 minutes

	await db.create(authorizationCodeTable, {
		code,
		client_id: data.clientId,
		subject_id: data.subjectId,
		session_id: data.sessionId,
		redirect_uri: data.redirectUri,
		scope: data.scope?.join(" ") ?? null,
		nonce: data.nonce ?? null,
		pkce_challenge: data.pkce?.challenge ?? null,
		pkce_method: data.pkce?.method ?? null,
		auth_time: Math.floor(now / 1000),
		expires_at: now + TTL,
		created_at: now,
	});

	return code;
}
```

The PKCE parameters are optional to maintain backward compatibility with clients that do not support PKCE. However, enforce PKCE for public clients as required by OAuth 2.1.

## Verify the Code Verifier at Token Exchange

When the client exchanges the authorization code for tokens, it sends the original code verifier. The server must verify it matches the stored challenge.

First, parse the token request and extract the code verifier.

```ts {% path="lib/schemas.ts" %}
import * as s from "remix/data-schema";

let AuthorizationCodeSchema = s.object({
	grant_type: s.literal("authorization_code"),
	code: s.string(),
	redirect_uri: s.string(),
	client_id: s.optional(s.string()),
	client_secret: s.optional(s.string()),
	code_verifier: s.optional(s.string()),
});
```

Then implement the verification function that supports both S256 and plain methods.

```ts {% path="lib/pkce.ts" %}
async function validatePKCE(
	verifier: string,
	challenge: string,
	method: "S256" | "plain",
): Promise<boolean> {
	if (method === "plain") {
		return verifier === challenge;
	}

	let encoder = new TextEncoder();
	let data = encoder.encode(verifier);
	let hash = await crypto.subtle.digest("SHA-256", data);
	let generatedChallenge = btoa(String.fromCharCode(...new Uint8Array(hash)))
		.replace(/\+/g, "-")
		.replace(/\//g, "_")
		.replace(/=/g, "");
	return generatedChallenge === challenge;
}
```

The verification recreates the challenge from the verifier using the same transformation applied during authorization. For S256, it hashes the verifier and compares. For plain, it does a direct string comparison.

## Integrate Verification into the Token Endpoint

Integrate PKCE verification into your token endpoint handler. The verification happens after consuming the authorization code but before issuing tokens.

```ts {% path="lib/token-handler.ts" %}
async function handleAuthorizationCode(db: Database, body: Record<string, unknown>) {
	let result = await validate(body, AuthorizationCodeSchema);
	if (isFailure(result)) {
		return reject("invalid_request", "Missing or invalid parameters");
	}

	let { code, redirect_uri, code_verifier } = result.data;

	// Consume the authorization code (single-use per RFC 6749)
	let authzData;
	try {
		authzData = await AuthorizationCode.consume(db, code);
	} catch (error) {
		if (error instanceof AuthorizationCode.AlreadyConsumedError) {
			return reject("invalid_grant", "Authorization code has already been used");
		}
		if (error instanceof AuthorizationCode.ExpiredCodeError) {
			return reject("invalid_grant", "Authorization code has expired");
		}
		throw error;
	}

	// Verify redirect URI matches
	if (redirect_uri !== authzData.redirectUri) {
		return reject("invalid_grant", "Redirect URI mismatch");
	}

	// Get the client to check type
	let client = await Client.show(db, authzData.clientId);
	if (!client) {
		return reject("invalid_client", "Client not found", 401);
	}

	// PKCE is required for public clients per OAuth 2.1
	if (client.type === "public" && !authzData.pkce) {
		return reject("invalid_request", "PKCE is required for public clients");
	}

	// Verify PKCE if it was used during authorization
	if (authzData.pkce) {
		if (!code_verifier) {
			return reject("invalid_request", "Missing code_verifier");
		}

		let isValid = await validatePKCE(
			code_verifier,
			authzData.pkce.challenge,
			authzData.pkce.method,
		);

		if (!isValid) {
			return reject("invalid_grant", "PKCE validation failed");
		}
	}

	// Continue with token issuance...
}
```

The handler enforces several rules: if the authorization request included PKCE, the token request must include the verifier; public clients must always use PKCE; and the verifier must produce the same challenge stored during authorization.

## Handle Verification Failures

PKCE verification can fail for several reasons. Return appropriate error codes to help clients debug issues.

```ts {% path="lib/responses.ts" %}
function reject(error: string, description: string, status = 400): Response {
	return new Response(
		JSON.stringify({
			error,
			error_description: description,
		}),
		{
			status,
			headers: {
				"Content-Type": "application/json",
				"Cache-Control": "no-store",
			},
		},
	);
}
```

Common error scenarios include `invalid_request` with "Missing code_verifier" when the authorization used PKCE but the token request omitted the verifier, `invalid_grant` with "PKCE validation failed" when the verifier does not match the challenge (indicating a potential attack or client bug), and `invalid_request` with "PKCE is required for public clients" when a public client attempted authorization without PKCE.

## Enforce PKCE for Public Clients

OAuth 2.1 mandates PKCE for public clients (SPAs, mobile apps, native apps) because they cannot securely store client secrets. Enforce this at both the authorization and token endpoints.

At the authorization endpoint, require PKCE parameters for public clients:

```ts {% path="lib/authorize-handler.ts" %}
if (client.type === "public") {
	if (!code_challenge || !code_challenge_method) {
		return redirect(`${redirect_uri}?error=invalid_request&error_description=PKCE+is+required`);
	}
}
```

At the token endpoint, verify PKCE was used and the verifier is present (as shown in the handler above).

Confidential clients (server side applications) can also use PKCE for defense in depth, even though they authenticate with client secrets.

## Test the PKCE Implementation

Test your PKCE implementation with these scenarios: valid verifier produces matching challenge, different verifier fails validation, token request without verifier is rejected when PKCE was used, verifier equals challenge for plain method, and public client without PKCE is rejected.

```ts {% path="lib/pkce.test.ts" %}
import { describe, expect, test } from "bun:test";

describe("PKCE validation", () => {
	test("validates S256 correctly", async () => {
		let verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk";
		let challenge = "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM";

		let result = await validatePKCE(verifier, challenge, "S256");
		expect(result).toBe(true);
	});

	test("rejects invalid verifier", async () => {
		let verifier = "wrong-verifier";
		let challenge = "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM";

		let result = await validatePKCE(verifier, challenge, "S256");
		expect(result).toBe(false);
	});

	test("validates plain correctly", async () => {
		let verifier = "test-verifier";
		let challenge = "test-verifier";

		let result = await validatePKCE(verifier, challenge, "plain");
		expect(result).toBe(true);
	});
});
```

## Final Thoughts

PKCE is essential for securing OAuth flows, especially for public clients. By generating a random verifier, transforming it into a challenge, and verifying the binding at token exchange, you prevent authorization code interception attacks. Always use the S256 method and enforce PKCE for all public clients.
